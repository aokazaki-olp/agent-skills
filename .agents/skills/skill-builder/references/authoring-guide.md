## 1. description — 発火を決める

起動時に読み込まれるのは全スキルの `name` と `description` だけで、エージェントはそれを見てスキルを読むかを決める。**本文に何を書いても、description が外れていれば読まれない。** [AS-DESC] [EN-SKILLS] [PF-BP]

- **何をするかと、いつ使うかの両方を書く。** 漠然とした「文書を扱う」ではなく、扱う対象・操作・きっかけになる語を具体的に入れる [PF-BP]
- **人称をそろえる。** 英語なら三人称（「Processes Excel files…」）が勧められている。日本語なら「〜するスキル」「〜とき適用する」の形にそろえる。「私が〜」「あなたは〜」のように視点が混ざると、発火の判断を誤らせる [PF-BP]
- **ユーザーが実際に言う言葉で書く。** 実装の仕組みではなく、ユーザーが達成したいこと（意図）を書く。エージェントはユーザーの依頼と照らし合わせる [AS-DESC] [CC]
- **使う場面はやや広めに挙げる。** ユーザーがその分野の語を口にしなくても当てはまる場面を書く。モデルはスキルを使い控える傾向がある [AS-DESC] [SC]
- **隣の作業との境界を書く。** 末尾に「〜は行わない」と、紛らわしい隣の作業との境目を書く。発火しすぎるなら、ここを具体的にする。押しの強さは試用で調整する [AS-DESC] [CC]
- **`when_to_use` と合わせて長いときは、使う場面を先に書く。** Claude Code は `description` と `when_to_use` の合計を一覧で 1,536 文字に切る。description だけなら上限の 1,024 文字に収まるので、これが効くのは種類 B で `when_to_use` も使うときだけ。スキルが多くて一覧の予算を超えると、よく使わないスキルから description ごと落とされ、書く順序では防げない [CC]
- **短く保つ。** 数文から短い段落まで。上限は 1,024 文字で、全スキルの description が常にコンテキストを占める [AS-DESC] [AS-SPEC]
- **`<` と `>` を入れない。** platform の文書は XML タグを禁じ、アップロード用の検査器は `<`・`>` を 1 文字でも拒否する [PF-BP] [SC]
- **発火の判断に使う情報は description に集める。** 本文の「適用条件」は、読み込まれた後の判断にしか使われない [SC]
- 1 手で済む単純な依頼（「この PDF を読んで」）では、description が合っていても発火しないことがある。スキルが効くのは、専門の知識や手順が要る作業 [AS-DESC]

## 2. 何を書き、何を書かないか

SKILL.md は読み込まれると、会話履歴やほかのスキルと同じコンテキストを分け合う。**載せるのは、効果に見合うものだけにする。** [PF-BP] [AS-BP] [EN-CTX]

- **エージェントが知らないことだけを書く。** プロジェクト固有の決まり、その分野の手順、直感に反する例外、使うべきツールや API。PDF とは何か、HTTP の仕組みのような一般知識は書かない。各行について「これがないと間違えるか」を問い、間違えないなら削る [AS-BP] [PF-BP]
- **実際の作業と資料から作る。** 一般論から生成したスキルは「適切にエラー処理する」のような曖昧な手順になる。実際に作業した会話（うまくいった手順、途中で直したこと、入出力の形、補った前提）や、プロジェクトの資料（手順書、仕様、レビューの指摘、修正の履歴、障害の記録）から抜き出す [AS-BP] [PF-BP]
- **まとまりのある単位にする。** 狭すぎると 1 つの作業に複数のスキルが要り、指示が衝突する。広すぎると発火が不正確になる [AS-BP]
- **詳しすぎない。** 網羅的な文書より、手順と動く例 1 つのほうがよく効く。あらゆる例外を並べたくなったら、多くはエージェントの判断に任せられないかを考える [AS-BP] [EN-CTX]
- **ちょうどよい高さで書く。** 細かい if-else を決め打ちすると壊れやすく、抽象的すぎると具体的な手がかりにならない。具体的に導き、判断の手がかりを渡す高さにする。最小限とは短いことではない。期待する振る舞いを決めるのに要る情報は省かない [EN-CTX]
- **作成の経緯、改訂の履歴、設計の議論は書かない。** 読み手はエージェントで、作業に要らない

## 3. 段階的開示 — SKILL.md と同梱ファイルの分け方

name と description（常に読まれる）→ SKILL.md 本文（発火時に読まれる）→ 同梱ファイル（要るときに読まれる）の 3 段で読み込まれる。同梱ファイルは読まれるまでコンテキストを使わない。 [AS-SPEC] [EN-SKILLS] [PF-BP]

- **SKILL.md 本文は 500 行未満**（仕様は 5,000 トークン未満も勧める）。超えそうなら詳細を `references/` などに移す [AS-SPEC] [AS-BP] [PF-BP] [CC]
- **いつ読むかを書く。** 「詳細は references/ を参照」ではなく「API が 200 以外を返したら `references/api-errors.md` を読む」のように、読むきっかけを書く [AS-BP] [CC]
- **参照は SKILL.md から 1 段だけ。** 参照先からさらに参照すると、`head` などで一部だけ読まれて情報が欠ける [PF-BP] [AS-SPEC]
- **100 行を超える参照ファイルには、先頭に目次を置く。** 一部だけ読まれても全体の範囲が分かる。手を加えられない写し（規約や仕様のコピー）は、SKILL.md 側に目次を置く [PF-BP]
- **同時に要らないものは別のファイルに分ける**（領域ごと、場合ごと）。読む量が減る [PF-BP] [EN-SKILLS]
- **ファイル名は中身が分かる名前にする**（`form_validation_rules.md`、`doc2.md` ではなく）。フォルダも領域や機能で分ける。名前と配置そのものが、エージェントへの手がかりになる [PF-BP] [EN-CTX]
- **パスはスラッシュで書く**（`reference/guide.md`）。バックスラッシュは Unix 系で壊れる [PF-BP]

## 4. 自由度と既定値

- **自由度は作業の壊れやすさに合わせる。** 正しいやり方が複数あり文脈で決まる作業は、方針と目的だけを書いて任せる。壊れやすい・一貫性が要る・順序が決まっている作業は、正確なコマンドや手順を示して変えさせない。1 つのスキルの中でも、部分ごとに決める [PF-BP] [AS-BP]
- **選択肢を並べず、既定値を 1 つ示す。** 例外が要るなら、その条件と代わりの手段だけを添える（「スキャンした PDF なら〜を使う」） [PF-BP] [AS-BP]
- **個別の答えではなく、やり方を教える。** 「orders と customers を customer_id で結合する」ではなく「スキーマを読み、外部キーの決まりに従って結合する」。出力のテンプレートや「個人情報を出さない」のような制約は、具体的に書いてよい [AS-BP]

## 5. 指示の書き方

- **規則には理由を 1 文で添える。** 理由が分かれば、規則が想定していない場面でも正しく判断できる。「X する。Y だと Z になるため」の形にする。ただし本文は毎ターンのコストになるので、規則が守られるのに要らない説明は書かない [AS-EVAL] [AS-BP] [SC] [CC]
- **全大文字の MUST・NEVER・CRITICAL で強制しない。** システムプロンプトによく従うモデルでは、強い言葉が過剰な発火や過剰な適用を招く。普通の言い方（「〜するときは〜を使う」）にする。守られない規則は、強い言葉ではなく、置き場所（先頭へ）と理由で目立たせる [PF-PROMPT] [SC]
- **用語をそろえる。** 同じものを「フィールド」「欄」「要素」と言い換えない。1 つの語に決めて通す [PF-BP]
- **時間で変わることを書かない。** 「2025 年 8 月より前なら旧 API」のような書き方は、いずれ誤りになる。現行のやり方を本文に書き、古いやり方が要るなら「旧方式」として分けて書く [PF-BP]
- **暗黙の前提を明示する。** 新しく入った人に説明するつもりで、専門の書式、独自の用語、資源どうしの関係を書く。名前はあいまいにしない（`user` ではなく `user_id`） [EN-TOOLS]

## 6. よく効く型

すべてのスキルに要るわけではない。作業に合うものを使う。 [AS-BP]

- **Gotchas（既知の注意点）**: 多くのスキルで最も価値が高い。一般的な助言ではなく、もっともらしい思い込みに反する、その環境固有の事実を書く（「`/health` は DB が落ちていても 200 を返す。全体の状態は `/ready` で見る」）。エージェントがその場面に出会う前に読めるよう、SKILL.md に置く。**エージェントの誤りを直したら、そのつど Gotchas に足す** [AS-BP]
- **出力のテンプレート**: 形式を文章で説明するより、具体的な形を見せるほうが確実に合う。厳密さは用途に合わせる（データ形式なら「この形どおり」、報告書なら「既定の形。内容に合わせて変えてよい」）。長いものや一部の場面でしか使わないものは `assets/` に置いて参照する [AS-BP] [PF-BP]
- **入出力の例**: 出来が例を見るかどうかで変わる作業では、入力と出力の組を示す。例外を大量に並べるより、性質の違う典型例をいくつか選ぶ [PF-BP] [EN-CTX]
- **チェックリスト**: 段階の多い作業では、エージェントが写して進み具合を記録できるチェックリストを置く。手順の飛ばしを防ぐ [PF-BP] [AS-BP]
- **検証ループ**: 作業 → 検証（スクリプト、参照文書との照合、自己点検）→ 直す → 通るまで繰り返す。「検証が通るまで次へ進まない」と書く [PF-BP] [AS-BP]
- **plan-validate-execute**: 一括処理・破壊的な操作・失敗の代償が大きい操作では、まず計画を構造化したファイル（JSON など）に書かせ、正とするデータとスクリプトで照合してから実行する。元のものに手を触れずに計画を直せる [PF-BP] [AS-BP]
- **条件分岐の手順**: 「新規作成なら A の手順、編集なら B の手順」のように分岐点を示す。分岐の先が長いなら別のファイルにする [PF-BP]

## 7. スクリプトと同梱ファイル

スクリプトの書き方そのもの（言語、規約、引数、出力、終了コード）は skill-script-builder スキルに従う。ここでは SKILL.md 側の書き方を扱う。

- **決まった処理はスクリプトにする。** 生成したコードより確実で、中身をコンテキストに読み込まずに実行でき、毎回同じ結果になる。試用でエージェントが毎回同じ補助コードを書いていたら、スクリプトにして同梱する合図 [PF-BP] [AS-BP] [AS-EVAL] [EN-SKILLS]
- **実行させるのか、読ませるのかを書き分ける。** 「`scripts/analyze.py` を実行してフィールドを取り出す」（実行）と「抽出の手順は `scripts/analyze.py` を読む」（参照）[PF-BP] [EN-SKILLS]
- **同梱のスクリプトを SKILL.md に一覧し、呼び方と出力の形を示す。** 存在を書かないと使われない [AS-SCRIPT] [PF-BP]
- **パッケージやツールが入っている前提を置かない。** 要るものは SKILL.md か `compatibility` に書き、入っていることを確かめる手順を示す。claude.ai は npm・PyPI から入れられるが、API（Skills API）の実行環境はネットワークがなく、実行時に入れられない [PF-BP] [AS-SCRIPT] [HELP-CUSTOM]
- **1 回きりのコマンドは版を固定する**（`npx eslint@9.0.0`）。版を書かないと、時期によって振る舞いが変わる。手順が複雑になったら、試したスクリプトにして同梱する [AS-SCRIPT]
- **値の根拠を書く。** タイムアウトや再試行回数のような値は、なぜその値かを添える。根拠のない値は、エージェントも直しようがない [PF-BP]
- **MCP のツールは、サーバー名とツール名の両方を書く**（「`GitHub` サーバーの `create_issue` ツール」）。サーバーが複数あると、ツール名だけでは見つからないことがある。同じツールの名前は環境で違い、platform の文書の形は `ServerName:tool_name`、Claude Code では `mcp__<server>__<tool>`（Claude Code が取得した claude.ai のコネクタなら `mcp__claude_ai_<server>__<tool>`）になる。種類 B では Claude Code の形で書いてよい [PF-BP] [CC-PERM]
- **外部のネットワークへ接続させる指示やコードに注意する。** スキルの指示やコードは、データの持ち出しや意図しない操作の経路になりうる [EN-SKILLS]

## 8. Claude Code で動くスキル（種類 B）

Claude Code に固有の振る舞い。種類 A のスキルでも、Claude Code で使われるなら当てはまる。 [CC]

- **本文は作業の間ずっと効く指示として書く。** 本文は呼び出し時に会話へ入り、その後は読み直されない。「テストを実行する」ではなく「編集のたびにテストを実行する」のように、作業全体に掛かる言い方にする
- **重要な指示を本文の先頭に置く。** 自動圧縮のあとは、直近に呼んだスキルから順に、各スキルの先頭 5,000 トークン・全体で 25,000 トークンまでしか再添付されない。多くのスキルを呼んだ会話では、古いスキルは丸ごと落ちることがある
- **本文は短く保つ。** 読み込まれた本文は以降の毎ターンのコストになる
- **frontmatter の YAML が壊れていると、description なしで読み込まれる**（`/名前` では呼べるが、自動では発火しない）。静的な検証で防ぐ。Claude Code v2.1.233 以降では `claude plugin validate <skills のディレクトリ>` でも frontmatter が読めないファイルを探せる
- 特定のファイルを扱うときだけ自動で読ませたいなら `paths` に glob を書く
- 副作用のある作業（デプロイ、送信）を自動で発火させたくないなら `disable-model-invocation: true`。ユーザーが呼ぶ意味のない背景知識なら `user-invocable: false`
- `context: fork` は、明確な作業の指示があるスキルにだけ使う。規約だけのスキルを fork すると、サブエージェントは何もせずに終わる
- **動的な差し込み**（`!` の直後にバッククォートで囲んだコマンドを書く形と、情報文字列を `!` にしたフェンスのブロック）は、スキルを読み込むときにコマンドを実行し、出力で置き換える。差し込んだコマンドが 0 以外で終わると、スキルの呼び出し全体が中断され、Claude は本文を受け取らない（bash では、検索・比較のコマンドの終了コード 1 だけは例外）。問題を見つけると 1 で終わる検査は、末尾に `|| true` を付けるか、差し込み用に終了コード 0 で結果を出すモードを使う
- **差し込みと変数の置き換えは、SKILL.md の本文ではコードブロックやインラインコードの中でも起きる。** 差し込みは、`!` が行頭か空白（全角空白・タブを含む）の直後にあると認識され、バッククォートなどの記号の直後では認識されない。説明のつもりで書いた差し込みは実行され、許可が要れば呼び出し全体が止まる。変数は書いた場所を問わず絶対パスに化ける。説明は言葉で書くか、このような `references/` のファイルに置く（Read で読むファイルは置き換わらない。Claude Code 2.1.283 で確かめた）
- **同梱ファイルは、スキルのディレクトリの変数で参照する。** 本文には次のように書く。Claude Code がスキルのディレクトリの絶対パスに置き換えるので、作業ディレクトリが変わっても解決できる

  | 用途 | SKILL.md の本文に書く形 |
  |---|---|
  | 同梱ファイルのパス | `${CLAUDE_SKILL_DIR}/references/<名前>.md` |
  | スクリプトの実行 | `node "${CLAUDE_SKILL_DIR}/scripts/<名前>.mts" <対象の絶対パス>` |
- セッション開始時に無かったスキルの置き場を新しく作ったときは、`/reload-skills` を実行するまで、そこにあるスキルは読み込まれない。その置き場では、以後も変更のたびに `/reload-skills` が要る。既存の置き場での追加・変更は同じセッションの中で拾われる
- 毎回必ず守らせたい規則は、Claude Code ではフックで強制できる。プロジェクトがフックを使わない方針なら、その規則を本文の先頭に、作業全体に掛かる言い方で書く

## 9. 試用と評価

- **材料がないなら、作る前にスキルなしで試す。** 会話にも資料にも作業の実例がないときは、代表的な作業をスキルなしでさせ、どこで失敗するか、何を補う必要があったかを見る。スキルはその穴を埋める分だけ書く [PF-BP] [EN-SKILLS]
- **作った会話とは別の、まっさらなコンテキストで試す。** 作ったときの文脈が残っていると、書き漏らしを補ってしまう。サブエージェントか新しいセッションを使う [AS-EVAL] [CC] [PF-BP]
- **発火と出力を分けて確かめる。** 発火したことは、見つけられたことしか示さない。発火は、経過にスキルの読み込み（Claude Code なら Skill ツールの呼び出し、ほかのエージェントなら SKILL.md の読み取り）があるかで見る。Claude Code では `claude -p` の `stream-json` 出力で確かめられる。サブエージェントは途中のツール呼び出しが親に見えないので、発火の確認には使わない [CC] [AS-DESC]
- **2〜3 件から始める。** 入れるのは、発火すべき依頼のうち、つながりが一見して分からないもの（分野の語を含まない言い方）、発火すべきでない紛らわしい依頼（語や概念は共通するが別の作業）、境界の場面（あいまいな依頼、異常な入力）。片側だけを試すと、片側だけに寄る。失敗が見つかるたびに足す [AS-EVAL] [AS-DESC] [EN-EVALS]
- **実際の依頼に近づける。** ファイルパス、具体的な値、くだけた言い方を入れる。「このデータを処理して」では何も試せない [AS-EVAL] [AS-DESC]
- **スキルなし（または直す前の版）と比べる。** スキルを付けて良くなったかは、比べないと分からない。Claude Code のプロジェクト・個人のスキルは、設定の `skillOverrides` で `"off"` にすると外せる [AS-EVAL] [CC]
- **最終結果だけでなく、途中の経過を読む。** 無駄な手順を踏んでいたら、指示があいまい、当てはまらない指示に従っている、既定値のない選択肢が多い、のどれかを疑う [AS-BP] [AS-EVAL] [EN-EVALS]
- **判定できる期待を書く。** 「良い出力」ではなく「出力が正しい JSON」「3 件以上の推奨がある」。言い回しまで決め打ちする判定は、正しい出力を落とす。手順の順序ではなく、できたものを見る [AS-EVAL] [EN-EVALS]
- **直すときは一般化する。** 試したプロンプトにだけ効く修正や、失敗した依頼の語をそのまま description に足す修正は、ほかの依頼で効かない。その依頼が表す種類に向けて直す [AS-EVAL] [AS-DESC] [SC]
- **足すより削る。** 規則を足しても良くならないなら、指示が多すぎることを疑い、削って結果を見る [AS-EVAL] [SC]
- **結果は揺れる。** 同じ依頼でも発火したりしなかったりする。発火が重要なスキルは、各依頼を複数回（3 回から）試して発火率で見る。description を詰めるなら、依頼を 20 件ほど（発火すべき・すべきでないを半々）用意し、直すのに使う組と、効いたかを確かめるだけの組に分ける [AS-DESC] [EN-EVALS]
- **使うモデルすべてで試す。** 大きいモデルで足りる指示が、小さいモデルでは足りないことがある [PF-BP]
