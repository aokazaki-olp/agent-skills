# 作り手ペルソナの層の書き方

目次: ファイル構成 / 根拠の区別 / lint が検査する形 / §1 bio / §2 translation / §3 memories / §4 tensions / §5 signatures / §6 dislikes / §7 voice / §8 moodboard / §9 PERSONA.md

## ファイル構成

| ファイル | 中身 | 演じるときに読む |
|---|---|---|
| `PERSONA.md` | 入口。人物像の要約、読むファイル、役割ごとの演じ方、出力の約束、自己批評 | ○ |
| `translation.md` | 判断のルール表（`T`・`M`） | ○ |
| `tensions.md` | 抑える場所と、にじませてよい場所 | ○ |
| `signatures.md` | さりげなく毎回出る癖（`S`、2〜3 個） | ○ |
| `dislikes.md` | 嫌いなものと感情的な理由（`D`） | ○ |
| `voice.md` | 口調、独り言のサンプル、批評の言い方 | ○ |
| `moodboard/README.md` | 集める参照画像と、各画像から拾うもの | 迷ったとき |
| `bio.md` | 人格設定（固有名詞） | 設計の素材 |
| `memories.md` | 経験と、そこから生まれた判断 | 設計の素材 |
| `research.md` | 調査の出典（`R`） | 設計の素材 |
| `log.md` | 採用・却下・批評・テストの記録 | 設計の素材 |

演じる側に素材（「設計の素材」のファイル）を読ませない。判断を決めるのはルール群で、素材まで読ませると読み込み量が増え、ルールへの注意が薄まる。

## 根拠の区別

bio.md の各項目（`- ` で始まる行）の末尾に、次のどれかを付ける。lint が検査する。

| 書き方 | 意味 |
|---|---|
| `〔出典: R1, R4〕` | research.md の出典で裏付けられている |
| `〔推測: R2〕` | 出典から推測した。現実にありうる組み合わせだが、そのものの出典はない |
| `〔仮〕` | 根拠がない。ユーザーに確かめるまでの仮置き |
| `〔指定〕` | ユーザーが依頼で指定したこと（「レシートを溜めがちな人」など） |
| `〔設計〕` | 人物の個性として設計で選んだこと（名前、年齢、持ち物の選び方など）。事実の主張ではない |

- 出典がその項目の内容（そういう人・行動・好みがある）を直接述べていれば `〔出典〕`。組み合わせや程度を出典から推し量ったなら `〔推測〕`
- 固有名詞の事実（製品の色、制度の時期など）は、`〔設計〕` にせず出典を付ける。出典が取れなければ、その固有名詞を使わないか `〔仮〕` にする
- ID を消しても、残りの ID を振り直さない。log.md が古い ID を参照しているため。欠番はそのままでよい。消したら log.md に `- 廃止: T3` の行を書く（lint はこの行にある ID を、定義のない ID として警告しない）

## lint が検査する形

表の列名、`###` の見出しの形（`### M1 …` など）、下の表に挙げた `##` の見出しを変えない。lint は次の形を前提に読む。bio.md の `##` の見出しは自由に変えてよい。表のセルに `|` を書くときは `\|` と書く。

| ファイル | 形 |
|---|---|
| `bio.md` | `- ` で始まる行が項目。各項目に根拠の区別。判断に効かせる項目に `[T#]` |
| `translation.md` | 列が「ID・由来・感性・判断」の表。ID は `T#` か `M#`。bio の `[T#]` と memories の `M#` のすべてに行がある |
| `memories.md` | `### M# 見出し` と、`- 今の判断:` の行（3〜5 個が目安） |
| `signatures.md` | `### S# 名前` と本文（2〜3 個が目安） |
| `dislikes.md` | 列が「ID・嫌いなもの・理由」の表。ID は `D#` |
| `voice.md` | `## 独り言サンプル` の下に `- 「…」` の行が 3 つ以上 |
| `research.md` | 列が「ID・主張・出典・取得日・種別」の表。取得日は `YYYY-MM-DD`、種別は決まった語（`references/research.md`） |
| `PERSONA.md` | 見出し「演じるときに読むファイル」「作業前の儀式」「出力の約束」「提出前の自己批評」 |

## §1 bio.md — 具体化

- カテゴリを固有名詞に置き換える。固有名詞は色・形・質感・価格帯・使われ方を運ぶ
- 「好き」だけでなく「どのくらい」「いつから」「どう接しているか」を書く
- 判断に効かせる項目に `[T1]` `[T2]` … を付ける。タグを付けた項目は translation.md に必ず行を持つ
- 生活の細部（持ち物・通勤・休日）は、見た目や手触りの情報を持つものを優先する
- タグのない項目があってよい（独り言の材料になる）。ただし半分を超えたら、判断に接続できないか見直す

| 悪い例 | 良い例 |
|---|---|
| 駅のサインが好き | 乗り換えのたびに案内サインの色と番号を目で追う。旅先でも最初に見るのは駅の案内図 [T2] 〔設計〕 |
| 文房具にこだわる | 製品名・色・太さまで書く。色ペンは持たない、のような「持たないもの」も書く |
| 経験豊富 | 何年、どんな会社で、どんな案件が何割か |

## §2 translation.md — 判断への変換（最重要）

- 1 行 = 1 つの ID。列は「ID・由来・感性・判断」
- **由来**: bio.md の項目（`T`）か、memories.md の記憶の見出し（`M`）
- **感性**: その設定から生まれる美的感覚・価値観。設定と判断の間に橋を架ける
- **判断**: 用途の領域で、第三者が出力を見て守れているかを判定できる具体的なルール。数値・個数・位置・禁止で書く
- 1 つの設定から判断が複数出てよい。判断の欄を `;` で区切る

| ID | 由来 | 感性 | 判断 |
|---|---|---|---|
| T2 | 案内サインの色と番号を目で追う | 色は飾りではなく、どこにいるかを伝える記号 | 色は意味（状態・区分）にだけ使い、1 つの意味に 1 色; 同じ画面で同じ色を別の意味に使わない |

よくある失敗:

- 判断が「分かりやすくする」「統一感を出す」のように形容詞に戻っている。守れたかを判定できないので効かない
- 設定と判断のつながりが飛んでいる。感性の欄で橋を架ける

## §3 memories.md — 記憶

- 3〜5 個。多すぎると焦点がぼける
- 見出しは `### M1 <見出し>`。各記憶は「いつ / 何があった / どう感じた / 今の判断」で書く
- 成功より、失敗・悔しさ・恥ずかしさのほうが強い意見を生む
- 「今の判断」は検証可能なルールにし、translation.md に同じ ID の行として写す

## §4 tensions.md — 葛藤

- 対立を書く。仕事と趣味に限らない（規定と好み、速さと丁寧さ、など）。その人物で最も判断を揺らす対立を選ぶ
- **抑える場所**と、**にじませてよい場所**を明示する。UI なら空の状態・完了画面・404・読み込み中・ツールチップなど、スライドなら表紙と扉、など
- にじませ方の上限を決める（1 画面 1 箇所まで、文言 1 行まで）
- プロジェクトにデザインシステムやブランドの規定があるなら、「規定が決めていて人格が触れない領域」と「規定が空けていて人格が決めてよい領域」もここに書く。書かないと、人格が規定を破るか、何も効かないかのどちらかになる

## §5 signatures.md — サイン

- 2〜3 個。4 個以上はくどい
- 見出しは `### S1 <名前>`。「見る人が見れば分かる」程度のさりげなさにする
- 出力を見て、入っているかを判定できる形で書く（値・位置・形）

## §6 dislikes.md — 嫌悪

- 表の列は「ID・嫌いなもの・理由」。理由は感情的な理由にする。理由のない嫌悪は、エージェントが場面によって無視する
- 生成 AI がやりがちなデザイン（紫から青のグラデーション背景、全要素の大きな角丸、すべて中央揃え、見出しの絵文字など）は、人格の言葉で嫌わせる

## §7 voice.md — 声

- `## 口調の特徴`: 語尾、口癖、言わない言葉を 3〜5 個
- `## 独り言サンプル`: 3 つ以上。`- 「…」` の形で書く。作業前の儀式で、エージェントがこれを手本にする
- `## 批評の言い方`: 順番、厳しさ、褒め方

## §8 moodboard/ — 画像

- 文字の説明より画像のほうが好みを強く伝える。画像はユーザーが用意する
- README には「集める画像の一覧」と「各画像から何を拾うか」を書く。拾うものは比率・間隔・色数など、判断に使える形にする

## §9 PERSONA.md — 入口

雛形（`assets/templates/maker/PERSONA.md`）の見出しをすべて残す。lint は「演じるときに読むファイル」「作業前の儀式」「出力の約束」「提出前の自己批評」の見出しを検査する。

- 用途を仮で決めた（依頼から読み取れなかった）ときは、用途の行の末尾に `〔仮〕` を付ける。lint が数え、ユーザーに確かめる対象になる
- 人物像の要約は 5 行程度。独り言の材料になる程度に具体的に書く（bio を読まずに儀式ができるように）
- 役割は「作る」と「批評する」。呼び出しで指定がなければ、依頼の内容から決め、どちらで動いたかを出力の先頭に書かせる
- 出力の約束: 判断・指摘ごとに根拠の ID（`T2`、`S1` など）を添える。どの ID にも当たらない判断は「ID なし」と書かせる（ルールの穴を見つける材料になる）
