# skill-builder スキル

## 目的

スキルを作る・直す作業を、聞き取りから配置の仕上げまで一本の手順にし、スキルの効果を引き出す書き方を毎回あてはめる。

---

## 前提：ほかのスキルとの分担

- 外部の仕様（frontmatter のキー、ツールの名前、CLI の引数、版）をスキルに書くときは [[research-workflow]] に従って確かめる。入っていなければ、公式の一次情報で確かめ、出典と確かめた版を控えてから書く。記憶で書いた仕様は、そのスキルを使うたびに誤りを広げる
- スキルにスクリプトを同梱するときは [[skill-script-builder]] に従う
- このスキルの同梱スクリプトは、`node <このスキルのディレクトリ>/scripts/<名前>.mts <対象の絶対パス>` の形で実行する。スキルのディレクトリ（読み込んだ SKILL.md がある場所）を基準にしたパスで実行し、`cd` はしない
- 同梱スクリプト（`scripts/validate-skill.mts`・`scripts/check-trigger.mts`）は Node.js 24.12 以上で動き、Linux・WSL・Windows のどれでも同じ 1 行で呼べる。依存パッケージは要らない

---

## 適用条件

- スキルを新しく作る、既存のスキルを直す・改名する・分ける
- 会話でしてきた作業や、プロジェクトの手順書を、スキルにまとめる
- description を書き直す（発火の具合を変える）
- 同梱ファイル（`references/`・`scripts/`・`assets/`）を足す・直す

既存のスキルを直すときも、手順 6〜9（検証・配置・試用・仕上げ）は省かない。小さな修正でも、name とディレクトリ名のずれや配置の食い違いは起きる。

---

## 書き方のチェックリスト

SKILL.md を書いている間と、書き終えたときに、毎回これで確かめる。各項目の詳しい内容と出典は `references/authoring-guide.md` にある。**初めてスキルを書くとき、またはどれかの項目で迷ったときは、その全文を読む。**

```
書き方のチェック:
- [ ] description: 何をするかと、いつ使うかの両方がある。ユーザーが実際に言う言葉が入っている
- [ ] description: 使う場面を広めに挙げ、「〜は行わない」と隣の作業との境界も書いた。< と > がない
- [ ] 本文: エージェントが知らないこと（固有の決まり・手順・例外・確かめた事実）だけを書いた。一般知識を書いていない
- [ ] 本文: 実際の作業や資料から抜き出した。一般論から作っていない
- [ ] 本文: 選択肢を並べず既定値を 1 つ示した。自由度を作業の壊れやすさに合わせた
- [ ] 本文: 個別の答えではなく、やり方（手順）を書いた
- [ ] 本文: 規則に短い理由を添えた。全大文字の MUST・NEVER で強制していない
- [ ] 本文: 用語がそろっている。時間で変わる書き方（「〜年より前なら」）がない
- [ ] 本文: 出力の形が決まっているならテンプレートか入出力の例を、段階の多い作業ならチェックリストと検証ループを置いた
- [ ] 本文: 一括・破壊的な操作は、計画を書かせて検証してから実行させる（plan-validate-execute）
- [ ] Gotchas: もっともらしい思い込みに反する事実を、本文の要約ではなく具体的に書いた
- [ ] 構成: 本文が 500 行未満。分けたファイルは SKILL.md から 1 段で参照し、いつ読むかを書いた。分けた参照ファイルが 100 行を超えるなら先頭に目次がある（手を加えられない写しは、SKILL.md 側に目次を置く）
- [ ] 構成: ファイル名が中身を表している。パスはスラッシュ区切り
- [ ] スクリプト: 実行させるのか読ませるのかを書き分けた。要るパッケージ・ツールの前提を書いた
- [ ] MCP ツール: サーバー名とツール名の両方を書いた（Claude Code では mcp__<server>__<tool> として現れる）
- [ ] スクリプトの呼び方: 手順 5 のとおりに書いた（種類 A は scripts/<名前>.mts と、基準のディレクトリ・cd しない・対象は絶対パスの一文）
- [ ] 種類 B のみ（A では飛ばす）: 重要な指示が本文の先頭にあり、作業の間ずっと効く言い方になっている
```

## 対象の種類を先に決める

スキルがどこで動くかで、使ってよい機能が変わる。**書き始める前に決める。** 依頼から明らかなら（「Claude Code 用に」「claude.ai でも使う」など）確かめずに進め、どちらにしたかを報告に書く。明らかでないときだけユーザーに聞く。迷ったら A にする。A は B の環境でもそのまま動くが、逆は動かない。

| 種類 | 動く場所 | 使ってよいもの |
|---|---|---|
| **A. 共通** | `.agents/skills/` を読むエージェント、Claude Code、claude.ai、Skills API、Claude Desktop の Cowork タブ | Agent Skills 仕様の範囲だけ |
| **B. Claude Code 専用** | Claude Code が動くところ: CLI、Claude Desktop の Code タブ（ローカル・SSH）、クラウドのセッション | Claude Code の拡張も使ってよい |

- Claude Code はプロジェクトの `.claude/skills/` と個人の `~/.claude/skills/` を読む。SSH のセッションは接続先の `~/.claude/skills/` を読む。クラウドのセッション（ルーティンを含む）は手元の `~/.claude/skills/` を読まず、クローンしたリポジトリの `.claude/skills/` と claude.ai のアカウントで有効にしたスキルを読む
- Cowork タブは claude.ai のアカウントで有効にしたスキルを使い、`~/.claude` を読まない。Cowork でも使うなら A にする
- B を選ぶのは、Claude Code の拡張（下の B の表）がないと目的を果たせないときだけ

### A の決まり

| 決まり | 理由 |
|---|---|
| frontmatter は `name` と `description` を基本にし、要るときだけ `license`・`compatibility`・`metadata` を足す | claude.ai へのアップロードと Skills API は、仕様の 6 フィールド（`name`・`description`・`license`・`compatibility`・`metadata`・`allowed-tools`）以外があると失敗する |
| `allowed-tools` は使わない | 仕様で Experimental。非対応のクライアントがある |
| ファイルはスキルのルートからの相対パスで参照する | 仕様の参照方法。スキルのディレクトリの変数（`CLAUDE_SKILL_DIR` をドル記号と波かっこで囲んだもの）は Claude Code でしか置き換わらない |
| SKILL.md は 1 つだけ。入れ子のスキルを作らない | アップロード系は SKILL.md が複数あると拒否する |
| 動的な差し込み（`!` の直後にバッククォートで囲んだコマンドを書く形と、情報文字列を `!` にしたフェンスのブロック）を使わない | claude.ai と API では動かず、Cowork ではプレースホルダーになる |
| MCP のツールは、サーバー名とツール名の両方を書く（「`GitHub` サーバーの `create_issue` ツール」） | ツール名だけではサーバーが複数あると見つからない。同じツールが、Claude Code では `mcp__<server>__<tool>`（Claude Code が取得した claude.ai のコネクタなら `mcp__claude_ai_<server>__<tool>`）、platform の文書では `ServerName:tool_name` と、環境ごとに違う名前で現れる |

### B の決まり

| 決まり | 理由 |
|---|---|
| Claude Code の拡張フィールド（`when_to_use`・`argument-hint`・`disable-model-invocation`・`context`・`paths` など）を使ってよい | Claude Code はキー名が一つでも違うと**黙って無視する**。キー名は Claude Code の skills 文書の frontmatter 表で確かめる |
| `hooks` は、プロジェクトがフックを使わない方針なら使わない | 方針は AGENTS.md などで確かめる |
| 同梱ファイルはスキルのディレクトリの変数（`CLAUDE_SKILL_DIR` をドル記号と波かっこで囲んだもの）で参照する。書き方の例は `references/authoring-guide.md` の「8.」にある | 作業ディレクトリが変わっても解決できる |
| ツールを制限したいときは `disallowed-tools` を使う | `allowed-tools` は「その回だけ許可の確認を省く」機能で、ほかのツールを禁じない |
| MCP のツールは `mcp__<server>__<tool>` の名前で書く | Claude Code でのツールの名前 |
| 重要な指示は本文の先頭に置く | 自動圧縮のあと、各スキルは先頭 5,000 トークンまでしか残らない |
| 本文は、作業の間ずっと効く指示として書く | 本文は一度読み込まれたら読み直されない。「最初に〜する」だけの手順は後半で効かない |

## 手順

### 1. 要件を会話から抜き出し、足りない分だけ聞く

次の 5 つを、まず**これまでの会話から**埋める。ユーザーが直前にしていた作業そのものをスキルにしたい場合が多く、うまくいった手順、途中で直したこと、入出力の形、補った前提はすでに会話にある。埋まらなかったものだけを聞く。

| 項目 | 決めること |
|---|---|
| 何をさせるか | スキルが定める手順・規約・知識。**しないこと**（ほかのスキルに委ねる範囲）も |
| いつ発火するか | ユーザーのどんな言い方・どんな状況で読まれるべきか。**発火してほしくない似た依頼**も |
| 出力 | ファイル、応答、コマンドの実行など。形式が決まっているなら、その形式 |
| 対象の種類 | A か B（上の節） |
| 置き場所 | どのプロジェクトのどこに正本を置くか。プロジェクトに配置の決まりがあるか |

会話にも資料にも作業の実例がないときは、先にスキルなしで代表的な作業を 1 回させ、どこで失敗するか・何を補う必要があったかを見る。スキルはその穴を埋める分だけ書く。

### 2. 名前を決める

| 決まり | 理由 |
|---|---|
| 1〜64 文字、`a-z`・`0-9`・`-` だけ。先頭・末尾のハイフンと `--` は不可 | Agent Skills 仕様 |
| ディレクトリ名と一致させる | 仕様 |
| `synced`・`anthropic-skills` にしない | Claude Code が読み込まない予約名 |
| `anthropic`・`claude` を含めない | claude.ai へのアップロードと Skills API で拒否される |
| 同じ置き場の既存スキル（外部から入れたものを含む）と同じ名前にしない | 入れ直したときに一方が上書きされる |

名前は何をするかが分かる語にする（`helper`・`utils`・`data` のような曖昧な語を避ける）。既存のスキルに命名の型（共通の接頭辞など）があれば合わせる。

### 3. 書く内容のうち、外部の仕様を確かめる

スキルが外部のツール・API・形式を扱うなら、一次情報で確かめてから書く（上の「前提」）。確かめた版がスキルの正しさに効くなら（CLI の引数、設定のキーなど）、本文にその版を書く。確かめられなかったことは書かないか、「未確認」と書く。

### 4. SKILL.md を書く

上の「書き方のチェックリスト」に沿って書く。書式は、同じプロジェクトに既存のスキルがあればその書き方（見出し、文体、description の組み立て、他のスキルの参照の書き方）に合わせる。なければ次を既定にする。

- frontmatter は、種類 A なら `name` と `description` だけから始める
- description は日本語なら「〜するスキル」の形で、次の順にする: 何をするスキルか／何を定めるか／いつ適用するか／他のスキルに委ねる範囲／末尾に「〜は行わない」。種類 B で `when_to_use` と合わせて 1,536 文字に近いときは、Claude Code が一覧で後ろを切るので、いつ適用するかを先に置く
- 長い description は `>-` の折り畳みで書く。値に `: ` を含むと YAML として不正になるので、引用符なしの 1 行に詰めない
- 本文の見出しは `# <name> スキル`。目的 → 前提（依存するスキル）→ 適用条件 → 本文 → 最後に `## Gotchas（既知の注意点）`
- 常体で「〜する」「〜しない」と書き、要点は太字にする
- 作成の経緯、改訂の履歴、なぜこの書き方にしたかは書かない。読み手はエージェントで、要るのは作業の指示と知識だけ

本文が 500 行に近づいたら、詳細を `references/` に分ける。

### 5. スクリプトが要るなら [[skill-script-builder]] に従う

毎回同じ手順を踏む処理、間違えると困る検査、長いコマンドはスクリプトにする。書き方・言語・呼び出し方・確認の仕方は [[skill-script-builder]] に従う。SKILL.md には、スクリプトの存在・呼び出し方・出力の読み方を書く。

SKILL.md での書き方と、実行時の呼び方は次のとおり。

- 種類 A（共通）: 本文には `scripts/<名前>.mts`（スキルのルートからの相対パス）と書き、実行時は `node <このスキルのディレクトリ>/scripts/<名前>.mts <対象の絶対パス>` と呼ぶ
- 種類 B（Claude Code 専用）: 本文にはスキルのディレクトリの変数（`CLAUDE_SKILL_DIR` をドル記号と波かっこで囲んだもの）に `/scripts/<名前>.mts` を続けたパスを書き、`node` にそのパスと対象の絶対パスを渡す。Claude Code が変数をスキルのディレクトリに置き換える。具体的な書き方は `references/authoring-guide.md` の「8.」を読む

どちらの種類でも、スキルのディレクトリ（読み込んだ SKILL.md がある場所）を基準にしたパスで実行し、`cd` はしない。処理の対象は絶対パスで渡す。種類 A の本文には、この一文を添える。

### 6. 静的な検証

同梱の検証スクリプトで、作ったスキルを検査する。このスキルのディレクトリを基準にしたパスで実行し、`cd` はしない。検査するスキルは絶対パスで渡す。

```
node <このスキルのディレクトリ>/scripts/validate-skill.mts --kind A <検査するスキルの絶対パス> [...]
```

- `--kind` は対象の種類（`A` か `B`）。A では仕様の 6 フィールド以外を error、`allowed-tools` を warning にする。B では Claude Code が認識しないキーと `hooks` を warning にし、claude.ai・API へのアップロードでだけ問題になるもの（`claude` を含む名前、1,024 文字を超える description、`<`・`>`）を warning に下げる。`name` と `description` は、Claude Code では省略できるが、発火と一覧に要るので、種類 B でも必須として扱う
- 検査: SKILL.md がルートに 1 つだけ（`node_modules`・`__pycache__`・ルート直下の `evals` は数えない）／1 行目からの frontmatter／name の規則とディレクトリ名の一致／避ける名前／description が 1〜1024 文字で `<`・`>` を含まない／使ってよいキー／YAML 1.1 で文字列にならない値（`yes`・`on`・`1.0`・日付など）／`license`（A のみ）・`compatibility`（1〜500 文字）・`metadata` が文字列／本文の Markdown リンクと、インラインコード中の `scripts/`・`references/`・`assets/`（種類 B では変数付きを含む）で始まるパスの参照先があり、バックスラッシュがない／本文（コードの中を含む）のスキルのディレクトリの変数（種類 A では error）と動的な差し込み（種類 A では error、B では warning）／シンボリックリンクのサブディレクトリ（warning。先は検査しない）／本文が 500 行未満
- 検査するディレクトリ自体がシンボリックリンク（`--copy` なしで入れた置き場など）なら、実体を検査し、JSON の `realPath` に実体のパスを出す
- 結果は JSON で stdout（`path` は絶対パス）、要約は stderr に出る。終了コードは 0（error と unverifiable なし）、1（どちらかあり）、2（使い方の誤り）
- `unverifiable` は、検査器が読めない YAML の書き方（アンカー、フロー形式の対応、複数行の引用符なしの値など）か、読み取りの失敗（権限がないなど）。その項目は検査されていない。**読める形に直すか、手で確かめる**
- 参照先の検査は、コードブロック（フェンスで囲んだものと、4 文字以上の字下げのもの）の中を見ない。拡張子のないパス、`<名前>`・`*` を含むパス、`$` を含むパス（種類 B のスキルのディレクトリの変数を除く）も見ない。そうした参照は手で確かめる。変数と差し込みの検査は、Claude Code の挙動に合わせてコードの中も見る

error と unverifiable がなくなるまで、直して検証し直す。検証が通っても、description の良し悪しや本文の正しさは分からない。それは手順 8 で確かめる。

### 7. エージェントが読む置き場へ入れる

試用の前に、スキルをエージェントが読み込む置き場へ入れる。正本を書いただけでは、試用のセッションに読み込まれない。

- **プロジェクトの AGENTS.md・README などに、置き場や入れ方の決まりがあれば、それに従う**（手順 9）
- 決まりがなければ、試用のために一時的に置き場（Claude Code ならプロジェクトの `.claude/skills/<名前>/`）へ写す。試用が終わったら、ユーザーに確かめたうえで片付けるか、そのまま本配置にする

### 8. 試用 — 発火と出力を分けて確かめる

作った会話の中で試さない。作るときの文脈が残っていると、本文に書き漏らしたことを補って動いてしまう。

1. 試すプロンプトを用意する。最初は次の 3 種類から 1 件ずつ。ファイルパスや具体的な値を入れ、ユーザーが実際に言う言い方で書く
   - 発火すべき依頼のうち、**つながりが一見して分からないもの**（スキルの分野の語を含まない言い方）
   - **発火すべきでない紛らわしい依頼**（同じ語や概念を含むが別の作業、隣のスキルの守備範囲）
   - **境界の場面**（あいまいな依頼、異常な入力、指示の解釈が分かれそうな場合）
2. **発火**を見る。Claude Code の CLI があるなら、同梱の `scripts/check-trigger.mts` で、新しいセッション（`claude -p`）を起こして判定する。どの OS でも同じ 1 行で動く。`--cwd` には、スキルを置いたプロジェクトのルートを渡す

   ```
   node <このスキルのディレクトリ>/scripts/check-trigger.mts --skill <スキル名> --prompt "<試すプロンプト>" --cwd <プロジェクトのルートの絶対パス>
   ```

   結果は JSON で stdout に出る。`verdict` は `triggered`（呼ばれ、エラーなく本文が返った）、`triggered (error)`（呼ばれたが、呼び出しがエラーになり本文が届かなかった。本文の差し込みに許可が要って止まった、など）、`not triggered`（呼ばれなかった）のどれか。**試用の完了条件は、発火すべき依頼で `triggered` と出たこと**。`not triggered` なら description を直し、`triggered (error)` なら本文を直す。**終了コード 1 は判定できていない**（未ログイン、打ち切りなど、claude 自体の失敗）。このときも JSON は出て、`verdict` が null、`error` に原因が入る。JSON の `claudeExitCode` と `claudeSignal` は、claude の終了コードと、シグナルで終わったときのシグナル名（それ以外は null）。description も本文も直さず、原因を先に解消する。終了コード 2 は、使い方の誤りか、claude を起動できなかった（見つからない、実行できない、Windows で `.cmd` を渡した）ことを示し、次の手が stderr に出る。既定では 600 秒で打ち切る。延ばすときは `--timeout <秒>` を付ける。`-` で始まるプロンプトは `--prompt=<プロンプト>` の形で渡す。Windows では、claude.exe のパスを `--claude` に渡すことがある

   - `claude -p` は、試したプロンプトの作業を実際に行おうとする。スクリプトは `--permission-mode dontAsk` を付けて起動し、確認が要る操作を断らせる。ただし、作業ディレクトリ内の読み取り、読み取り専用のコマンド、設定の許可ルール（`permissions.allow`）に当たる操作、PreToolUse hook が許可した呼び出しは実行される。書き込みや副作用が心配なら、プロジェクトの使い捨てのコピーで回す
   - Claude Code の CLI がないエージェントでは、新しいセッションで試し、経過に SKILL.md の読み取りがあるかを見る

3. **出力**を見る: 新しいセッションか、そのスキルを読み込んでいないサブエージェントに作業させる。サブエージェントから親に届くのは最終の報告だけで、途中のツール呼び出しは見えないので、発火の確認には使わない。最終結果だけでなく、出したファイルや手順の跡も確かめ、無駄な手順や指示の読み違いを探す。外れたら本文を直す
4. 違いが分かりにくいときは、スキルなし（または直す前の版）でも同じプロンプトを試して比べる。Claude Code のプロジェクト・個人のスキルは、設定の `skillOverrides` でそのスキルを `"off"` にすると外せる

直すときは、試したプロンプトにだけ効く修正をしない。その依頼が表す種類に向けて直す。エージェントの誤りを直したら、Gotchas に足す。直したら手順 6 から繰り返し、失敗が見つかるたびに試すプロンプトを足す。評価をさらに詰めるとき（発火率の測り方、期待の書き方）は `references/authoring-guide.md` の「9. 試用と評価」を読む。

### 9. プロジェクトでの仕上げ

**プロジェクトの AGENTS.md・README などに、スキルの置き場や入れ直しの決まりがあれば、それに従う。** 書かれていない配置を自分で決めない。決まりがなければ、置き場所をユーザーに確かめる。

正本のディレクトリから `npx skills add <正本の場所> ... --copy` でエージェントごとの置き場（`.agents/skills/`・`.claude/skills/` など）へ入れる構成なら、次を守る。

- 正本だけを編集する。入れた側（コピー）を直接直さない。次に入れ直したときに消える
- スキルを足したら、README のスキル一覧と、入れ直すコマンドのスキル指定（`-s`）に足す
- 正本から入れ直し、正本と入れた側が一致することを `diff -r <正本>/<名前> <入れた置き場>/<名前>` で、置き場ごとに確かめる
- `skills-lock.json` を消さない。エージェントの置き場（`.agents/skills/`・`.claude/skills/` など）にあるスキルのうち、lock に載っているものは、そのリポジトリを `npx skills add` しても配布されない。`skills/` など配布元に置いたスキルは配布される
- `npx skills update` を使わない。`--copy` で入れたものがシンボリックリンクに置き換わる

## Gotchas（既知の注意点）

- **Claude Code は SKILL.md の本文を、コードブロックやインラインコードの中も含めて走査する**。スキルのディレクトリの変数はどこに書いても置き換わり、行頭か空白（全角空白・タブを含む）の直後の `!` とバッククォートの組は、読み込むときに実行される。説明のつもりで書くと、変数は絶対パスに化け、差し込みは実行されて、許可が要れば呼び出し全体が止まる。説明は言葉で書くか、`references/` に置く（Read で読むファイルは置き換わらない）
- Claude Code は**知らないキーを黙って無視する**。キー名の綴り違い（`allowed_tools` など）はエラーにならず、効いていないだけになる
- description に `: ` を含めて引用符なしで 1 行に書くと YAML として壊れる。Claude Code はそのスキルを description なしで読み込み、自動では発火しなくなる
- `version: 1.0` のような引用符なしの値は、アップロード側の検査器（YAML 1.1）では文字列にならない
- 改名は、ディレクトリ名と `name` を同時に変え、入れた側の古いディレクトリも消す。古いほうが残ると、古い名前のスキルも読み込まれ続ける
- Claude Code はスキルの置き場の変更を、同じセッションの中で拾う。ただし、セッション開始時に無かった置き場（プロジェクトに初めて作った `.claude/skills/` など）は監視されていない。そこへ入れたスキルは、新しいセッションで試すか、ユーザーに `/reload-skills` を打ってもらう。その置き場では、以後も変更のたびに `/reload-skills` が要る
