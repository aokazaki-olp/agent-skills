# skill-script-builder スキル

## 目的

スキルに同梱するスクリプトを、**配布先の環境と作業ディレクトリに左右されず、エージェントが呼び出しと結果の読み取りを間違えない**形で書く。スクリプトは SKILL.md と違って中身がコンテキストに読み込まれず、出力だけが読まれる。だから、引数・出力・終了コードの約束事がそのままスキルの使いやすさになる。

---

## 前提：コーディング規約に従う

- **スクリプトを置くスキルの正本があるリポジトリに、自前のコーディング規約があれば、そちらを優先する。** なければ、同梱の `references/coding-rules.md` に従う
- `references/coding-rules.md` は写しなので手を加えず、目次も置かない。目次は下の「規約の目次」で代える
- **初めてスキル用のスクリプトを書くときは、規約を全文読む**（`head` などで一部だけ読まない）。節どうしが参照し合っていて、一部だけでは規則の範囲を取り違える。以後は、下の「規約の目次」と「規約の当てはめ方」で該当する節を探して読む
- スキルの構成、SKILL.md へのスクリプトの書き方は [[skill-builder]] に従う

## 適用条件

- スキルの `scripts/` にスクリプトを足す・直す
- [[skill-builder]] の手順 5 で、スクリプトが要ると決めた
- 既存のスキルのスクリプトを別の言語から Node に書き直す

## 言語とファイル形式

| 決まり | 理由 |
|---|---|
| **Node.js で書く。下限は Node 24.12**（型注釈の除去が stable になった版） | 方針として、Linux・WSL・Windows のどれでも入っていることが多く、入れやすい Node を選ぶ。型注釈の除去により、ビルドなしで TypeScript を実行できる |
| **拡張子は `.mts`** にし、`node` で直接実行する | `.ts` を ESM と CommonJS のどちらとして読むかは、置かれた場所から最も近い `package.json` で決まる。配布先のプロジェクトが `"type": "commonjs"` だと `import` で SyntaxError になり、`type` がないと警告を出して読み直す。`.mts` は常に ESM として読まれる |
| スキルのフォルダに `package.json`・`tsconfig.json` を置かない | 配布先のプロジェクトのツール（lint、型検査、ワークスペース）が拾い、予期しない設定になる |
| **依存パッケージを使わず、`node:` の組み込みモジュールだけで書く** | API（Skills API）の実行環境はネットワークがなく、実行時にパッケージを入れられない。インストールの手順もいらなくなる |
| 相対 import は実ファイルの拡張子まで書く（`./lib/args.mts`） | Node は書かれたとおりのファイルを探す |
| Node 以外の言語は、Node で書けない理由があるときだけ使う。その理由と前提（実行環境、版）を SKILL.md の本文か `compatibility` に書く | 前提が書かれていないと、エージェントは入っていない処理系で実行を試みる |

SKILL.md には「Node.js 24.12 以上が要る」ことを書く。種類 A（共通）のスキルなら本文か `compatibility` に、種類 B なら本文に書く。

## 呼び出し方と作業ディレクトリ

スクリプトがどこから呼ばれても同じに動くよう、**スクリプトを作業ディレクトリに依存させない**。

- 同梱ファイル（テンプレート、データ、ほかのスクリプト）は `import.meta.dirname` を基準に解決する。作業ディレクトリからの相対パスで開かない
- 処理の対象（ファイル、ディレクトリ）は引数で受ける。受けたパスは最初に `path.resolve` で絶対パスにする
- 出力に含めるパスは絶対パスにする。呼び出した側の作業ディレクトリが分からなくても、そのまま使える

SKILL.md での書き方と、実行時の呼び方は次のとおり。

- 種類 A（共通）: 本文には `scripts/<名前>.mts`（スキルのルートからの相対パス）と書き、実行時は `node <このスキルのディレクトリ>/scripts/<名前>.mts <対象の絶対パス>` と呼ぶ
- 種類 B（Claude Code 専用）: 本文にはスキルのディレクトリの変数（`CLAUDE_SKILL_DIR` をドル記号と波かっこで囲んだもの）に `/scripts/<名前>.mts` を続けたパスを書き、`node` にそのパスと対象の絶対パスを渡す。Claude Code が変数をスキルのディレクトリに置き換える。具体的な書き方は `references/invocation.md` を読む

どちらの種類でも、スキルのディレクトリ（読み込んだ SKILL.md がある場所）を基準にしたパスで実行し、`cd` はしない。処理の対象は絶対パスで渡す。種類 A の本文には、この一文を添える。

同梱のスクリプトを一覧し、それぞれの役割・呼び方・出力の形・終了コードの意味を書く。**実行させるのか、読ませるのか**を書き分ける。

## スクリプトの約束事

| 約束事 | 書き方 |
|---|---|
| 対話的な入力を求めない | 入力は引数・環境変数・stdin で受ける。エージェントは TTY のプロンプトに答えられず、待ったまま止まる |
| `--help` を持つ | 何をするか、引数とオプション、例、終了コードの意味を短く書く。エージェントは `--help` で使い方を知る |
| 結果は stdout、診断は stderr | 結果は JSON などの構造化した形で stdout に出す。進み具合・警告・要約は stderr に出す。混ぜると結果を機械で読めなくなる |
| 終了コードを使い分ける | 既定は `0` 成功、`1` 問題を見つけた・処理に失敗した、`2` 使い方の誤り。ほかの区別が要るなら足し、`--help` に書く。終了は `process.exitCode` に設定して返し、`process.exit()` を呼ばない（書き出し途中の stdout が切れることがある） |
| 失敗をエージェントに投げ返さない | 想定できる失敗（ファイルがない、権限がない、形式が違う）は、スクリプトの中で扱う。既定値で続けられるなら続け、そのことを stderr に出す。続けられないなら、何が起きたかを書いて終わる。素の例外のスタックトレースを渡してエージェントに考えさせない |
| エラーメッセージに次の手を書く | 何が悪いか、何を期待したか（受け取った値も）、次に何を試すかを書く。「Error: invalid input」だけでは、エージェントは同じ誤りを繰り返す |
| あいまいな入力は推測しない | 決めつけて進めず、何が足りないかをエラーで返す。値の候補が決まっているなら、候補を示す |
| 破壊的な操作には `--dry-run` を付ける | 何が起きるかを先に見せる。取り返しのつかない操作は、明示のフラグなしでは行わない。再実行しても壊れないようにする（エージェントは再試行する） |
| 出力の量を抑える | 大きくなりうる出力は、既定で要約か上限を設ける。打ち切ったら、打ち切った事実を出力に含める（黙って削らない） |
| 値の根拠を書く | タイムアウトや上限のような値は、なぜその値かを 1 行で添える。コメントは規約が認める範囲（外部仕様への準拠など）で書く |
| OS をまたいで動かす | パスは `node:path` で組み立てる（`/` を文字列でつながない）。一時ディレクトリは `os.tmpdir()` の下に `fs.mkdtempSync` で作り、終わったら消す。外部コマンドは `spawnSync(コマンド, 引数の配列)` で起動し、シェルの文字列を組み立てない。`rm`・`grep`・`mktemp` などの POSIX のコマンドを呼ばず、`node:fs` などで同じことをする。読み込むテキストの改行は `\r?\n` で分ける（Windows では CRLF のことがある）。結果が同じになる細部（一時ファイルの名前や置き場所）は OS に合った方法でよい |

## 規約の当てはめ方

スキルのスクリプトは「Node が直接実行するコード」なので、規約の全節が掛かる（§1.3）。ただし、スキルのフォルダには `package.json`・`tsconfig.json`・lint の設定がなく、置かない。そのため次のように当てはめる。

| 規約 | スキルのスクリプトでどうするか |
|---|---|
| §2.1 `"type": "module"` が必須 | `.mts` で書くことで満たす（常に ESM）。`package.json` は置かない |
| §2.2 相対 import の拡張子 | `.mts` まで書く |
| §2.4 ファイルヘッダー | ほかのスクリプトから import される共有モジュール（`scripts/lib/*.mts` など）にだけ付ける。実行する入口のスクリプトには付けない |
| §2.5 `index.ts` を唯一の入口に | 置かない。スクリプトはそれぞれが実行の入口で、外へ公開する API を持たない |
| §4.1 公開関数の戻り値型 | `export` するものに付ける。1 ファイルで完結するスクリプトは何も `export` しない |
| §4.7 `!`・`as`・`any` の許容枠 | lint がないので、抑制コメントは書かない。**使わずに書くことを既定にする**（値の有無を `if` で確かめる、`?? ''` で受ける、型ガードで絞る）。どうしても要るなら、§4.7 の「通常のコメントで理由」の形で、なぜ安全かを 1 行で書く |
| §6.1 ランタイムガード | コマンドライン引数、読み込むファイル、環境変数、stdin が境界。ここで検査し、型が付いていても省かない |
| §6.2 `toError()` と判定 | `catch (e)` の `e` は `unknown` として扱い、`Error.isError(e)` で判定する。`instanceof Error` と `as Error` は使わない。1 ファイルなら変換の関数を内部に持ち、複数のスクリプトで使うなら `scripts/lib/` の共有モジュールにする |
| §6.3・§6.4 独自のエラークラス | 1 ファイルのスクリプトでは作らない。「使い方の誤り」「問題を見つけた」のような区別は、判別子つきの戻り値（§4.5）で表して終了コードに対応させる。作る場合も、判定は `instanceof` ではなく `Error.isError` と `name` などの構造で行う |
| §6.5 TSDoc | 共有モジュールの `export` に付ける |
| §7 テスト | テストランナーの設定とテストファイルは同梱しない。下の「確認の手順」で、一時ディレクトリに作った入力に対して実行して確かめる |
| §8 機械強制の設定 | スキルには置かない。型検査は、一時的に入れたコンパイラに §8.1 のコンパイラ要求にあたるフラグを付けて回す（下の「型検査」）。lint は回さないので、§8.2 で lint が要るとされる項目は自分で読んで確かめる（下の「確認の手順」） |
| 付録 A 下限マーカー | 下限は Node 24.12（baseline）。表で Node 25 以上とされている API は使わない。表にない新しい API は、Node 24.12 に入っているかを確かめてから使う |

## 型検査

**Node は `.mts` を型注釈の除去だけで実行し、型を検査しない。実行が成功しても、型が正しいことの証明にならない。** 書いたら・直したら、必ず型検査を回す。

同梱の `scripts/typecheck.mts` で検査する。どの OS でも同じ 1 行で動く。

```
node <このスキルのディレクトリ>/scripts/typecheck.mts <検査するスキルのディレクトリか .mts の絶対パス> [...]
```

- スキルのディレクトリを渡すと、その `scripts/` の下の `.mts` をすべて検査する
- OS の一時ディレクトリの下に TypeScript と `@types/node` を入れて検査し、失敗したときも含めて消す。プロジェクトにもスキルにも何も残さない。消せなかったときは JSON の `leftoverTempDir` にそのパスが出る。版はスクリプトの定数で固定してあり、`--help` に出る。npm のレジストリに接続できることが要り、npm の通信の経過は stderr に出る。npm install は 300 秒（5 分）で打ち切る
- 結果は JSON で stdout に出る。`ok` は `true`（型エラーなし）、`false`（型エラーあり。`diagnostics` に一覧）、`null`（npm・tsc の失敗などで型検査できなかった。`error` に原因）のどれか。**`ok` が `null` なら型検査はできていない。型が正しいとみなさない**。終了コードは 0（型エラーなし）、1（型エラーがあるか、型検査できなかった）、2（使い方の誤り）
- スクリプトが付けるフラグは、規約 §8.1 のコンパイラ要求に対応する: strict（`--strict`）、消去可能な構文だけ（`--erasableSyntaxOnly`）、import / export の構文の保持（`--verbatimModuleSyntax`）、インデックスアクセスを厳しく（`--noUncheckedIndexedAccess`）、フォールスルーの検出（`--noFallthroughCasesInSwitch`）、`override` 必須（`--noImplicitOverride`）、実行環境の型定義だけで DOM なし（`--lib esnext` と `--types node`）、Node に合わせたモジュール解決（`nodenext`）。`--rewriteRelativeImportExtensions` は `.mts` まで書いた import を通すため
- 規約 §4.9 が採用しないとするフラグ（`exactOptionalPropertyTypes`、`isolatedDeclarations`）は付けない
- `@types/node` のメジャー版は、下限の Node（24）に合わせる。TypeScript の版を上げるときは `npm view typescript version` で最新を確かめ、スクリプトの版の定数を書き換え、下の「確認の手順」の「検査が効いている」を確かめ直す
- `--lib esnext` で型が通っても、Node 24 にその API があるとは限らない（§5.6）。付録 A の表で確かめる

## 確認の手順

書き終えたら、次を写して順に確かめる。

```
スクリプトの確認:
- [ ] 規約（正本のリポジトリのもの、なければ references/coding-rules.md）の該当する節を読んでから書いた
- [ ] 型検査が通った（`scripts/typecheck.mts`、終了コード 0）
- [ ] 検査が効いている: 初めて検査するとき・型検査のスクリプトを変えたときは、わざと型エラーを 1 つ入れて落ちることを確かめ、元に戻した
- [ ] lint の代わりに目で確かめた: any、`!`、`as`、enum・デコレータ・`accessor`、相対 import の `.js`、forEach、var、ブロックの省略と一行化、Yoda 条件、`.then()`、`==`（`== null` を除く）、未使用の変数
- [ ] `--help` が出て、終了コード 0
- [ ] 別の作業ディレクトリ（スキルの外）から呼んでも同じ結果になる
- [ ] 正常な入力で、stdout が想定どおりの形（JSON なら `JSON.parse` で読める）、パスは絶対パス、終了コード 0
- [ ] 問題のある入力で、終了コード 1 と、次の手が分かるメッセージ
- [ ] 使い方の誤り（引数なし、未知のオプション、ありえない値）で、終了コード 2
- [ ] 境界の値（上限ちょうど・上限を 1 つ超える・空・1 件）で、期待どおりに判定する
- [ ] 試すための入力は一時ディレクトリに作り、スキルのフォルダに残していない
```

**動いたことは、型が正しいことも、規約に沿っていることも示さない。** 型検査と目での確認を省かない。

## Gotchas（既知の注意点）

- 種類 A のスキルにスクリプトを同梱し、claude.ai や Skills API でも使うなら、その実行環境に Node 24.12 以上があるかを、そこで `node --version` を実行して確かめる。なければ、SKILL.md にその環境では使えないことを書く
- コンパイラが「拡張子に `.js` を付けよ」と提案しても従わない。実ファイルの `.mts` を書く（§2.2）
- **Windows では `npm`・`npx` などの `.cmd` を、シェルなしで起動できない**（Node の child_process の文書）。`shell: true` に引数の配列を渡す書き方は、引数がエスケープされず、Node 24 では実行時に非推奨の警告が出る（DEP0190）。npm は、`process.execPath`（今の node）で npm の `npm-cli.js` を直接動かす。Windows の公式 zip では node.exe の隣の `node_modules/npm/bin/npm-cli.js`、Linux では node の 1 つ上の `lib/node_modules/npm/bin/npm-cli.js` にある。見つからず `cmd.exe /d /c npm …` で起動するときは、引数を固定の文字列だけにする
- `spawnSync` に拡張子なしで渡した名前は、Windows でも `.exe` なら PATH から見つかるが、`.cmd` は見つからず ENOENT になる。`.cmd` のパスを直接渡すと EINVAL になる。利用者の入力（プロンプトなど）を引数に含むコマンドは、`.cmd` 経由で起動しない
- TypeScript 7 の `tsc` は、OS ごとのネイティブ実行ファイル（`@typescript/typescript-<OS>-<CPU>` パッケージ）で動く。`node_modules/typescript/lib/tsc.js` を `process.execPath` で動かせば、どの OS でもそれを呼び出す。`node_modules/.bin/tsc` は Windows では `.cmd` なので直接起動しない
- **SKILL.md の本文では、差し込みと変数の置き換えはコードブロックやインラインコードの中でも起きる**。呼び出し方の説明に変数をそのまま書くと絶対パスに化け、行頭か空白の直後に `!` とバッククォートの組を書くと、読み込むときに実行される。説明は言葉で書くか、`references/` に置く
- Claude Code の動的な差し込み（`!` の直後にバッククォートで囲んだコマンドを書く形）では、stderr が stdout に混ざって差し込まれる。また、コマンドが 0 以外で終わると、スキルの呼び出し全体が中断され、Claude は本文を受け取らない。差し込みで使うスクリプトには、問題を見つけても終了コード 0 で終わり、結果だけを stdout に出し、stderr には何も出さないモード（`--inject` など）を用意する
