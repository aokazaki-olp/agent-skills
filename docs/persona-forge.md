# persona-forge の設計

デザインの判断を担わせるペルソナを設計し、エージェントが演じられる形に落とし込み、効き目を検証して育てるスキル。この文書は、その範囲・構成と、決めたことの根拠をまとめる。Claude Code の仕様の出典は `docs/sources/` 内のパスで示す（2.1.289 時点、2026-10-05 取得。実装の前に出典で現行かを確かめる）。

## 範囲

| 行う | 行わない |
|---|---|
| ペルソナを設計する（用途の確定、種の収集、ネットでの調査、具体化、判断への変換） | ペルソナの使い方（何人を立てるか、どう回すか、案や意見のまとめ方、ペルソナ間の優先順位） |
| 落とし込む（`personas/<slug>/` の一式と、薄いサブエージェント定義） | ペルソナを演じて作業すること自体 |
| 検証する（lint、ルール遵守テスト、見分けテスト） | 本物の利用者による検証 |
| 育てる（使った結果のフィードバックをルールへ反映する） | |

使い方を決めないので、どんな使い方（1人で使う、複数を並べる、作り手と使い手を往復させる）でも壊れない接続面を持たせることを、このスキルの責任にする。

## 対象と配置

- 分野はデザイン（UI と UX）。成果物をコード・SVG・構造のあるデータで出せるものを対象にする。ラスター画像の生成、ロゴ・ブランドの立ち上げ、実物のプロダクトは対象外にする。ルールを守れたかを出力から判定できない、または作る数が少なく検証と育成が回らないため
- 種類は skill-builder の B（Claude Code 専用）。サブエージェント定義を生成し、調査をサブエージェントで並列に回すため。サブエージェントや保存先のない Web のチャットでは使えない
- 置き方は他の自作スキルと同じ。正本を `skills/persona-forge/` に置き、`npx skills add . -a universal claude-code --copy` で `.agents/skills/` と `.claude/skills/` に入れる。`.agents/skills/` の写しは Claude Code 以外のエージェントからは使えない（`CLAUDE_SKILL_DIR` が置き換わらない）ので、description に Claude Code が前提であることを書く
- 裏取りの作法のスキル（このリポジトリでは `research-workflow`）が入っている前提にする。SKILL.md では名前を固定せず「裏取りの作法のスキル（例: research-workflow）」と書く

## ペルソナの種類

| | 作り手 | 使い手 |
|---|---|---|
| 決めること | 作り手の好みで、どう作るか | 対象の層にとって、どう使えば迷わず気持ちいいか |
| 個性の源 | 好きなもの、持ち物、経歴 | 毎日使っているアプリ、使う状況、慣れている操作 |
| 役割 | 作る / 批評する | なぞる / 批評する |
| 怖いこと | 好みの押し付け | 想像上の人物への合わせ込み |

どちらも「固有名詞 → 感性 → 判断」の変換を骨格にする。属性（年齢・性別・職業）だけでは世間の平均像が出るので、個性は固有名詞・記憶・状況で作る。

## ファイル構成

### 作り手 `personas/<slug>/`

| ファイル | 中身 | 演じるときに読む |
|---|---|---|
| `PERSONA.md` | 入口。人物像の要約（5 行程度）、役割ごとの演じ方、出力の約束 | ○ |
| `translation.md` | 判断のルール表（下記） | ○ |
| `tensions.md` | 抑える場所と、にじませてよい場所、にじませ方の上限 | ○ |
| `signatures.md` | さりげなく毎回出る癖（2〜3 個） | ○ |
| `dislikes.md` | 嫌いなものと感情的な理由 | ○ |
| `voice.md` | 口調、独り言のサンプル、批評の言い方 | ○ |
| `bio.md` | 人格設定（固有名詞） | 設計の素材 |
| `memories.md` | 経験と、そこから生まれた判断 | 設計の素材 |
| `research.md` | 調査の出典 | 設計の素材 |
| `moodboard/README.md` | 集める参照画像と、各画像から拾うもの | 迷ったとき |
| `log.md` | 採用・却下・批評・テスト結果の記録 | 設計の素材 |

### 使い手 `personas/<slug>/`

| ファイル | 中身 | 演じるときに読む |
|---|---|---|
| `PERSONA.md` | 作り手と同じ | ○ |
| `context.md` | 使う状況（場所・姿勢・ながら作業・急ぎ具合・頻度）と、状況の中での葛藤（急ぎたいが間違えたくない など） | ○ |
| `translation.md` | 判断のルール表（期待・慣れ → 判断） | ○ |
| `journeys.md` | 目的を果たすまでの道のり。何手で終わってほしいか、どこで中断され、どう戻るか | ○ |
| `moments.md` | 気持ちいい瞬間と、引っかかる瞬間 | ○ |
| `voice.md` | 心の声。操作しながら思ったことを口に出す形（思考発話）のサンプル | ○ |
| `profile.md` | 使っているアプリ・サービス・道具（固有名詞） | 設計の素材 |
| `memories.md` | 痛い目を見た経験と、そこから生まれた期待 | 設計の素材 |
| `research.md`、`log.md` | 作り手と同じ | 設計の素材 |

演じるときに読む範囲を絞るのは、判断を決めるのがルール群であり、素材まで読ませると読み込み量が増えてルールへの注意が薄まるため。素材のうち判断になるもの（記憶から生まれた判断など）は、`translation.md` に行として持たせる。

### ルール ID

判断を持つ項目には ID を付け、演じるときの出力に根拠として添えさせる。

| 接頭辞 | 項目 | 置き場所 |
|---|---|---|
| `T` | 設定（bio・profile・context の項目）から導いた判断 | translation.md |
| `M` | 記憶から導いた判断 | translation.md（由来の記憶を memories.md に持つ） |
| `S` | サイン | signatures.md |
| `D` | 嫌悪 | dislikes.md |
| `J` | 道のりの期待 | journeys.md |
| `G` / `F` | 気持ちいい瞬間 / 引っかかる瞬間 | moments.md |

`translation.md` の列は「ID・由来・感性・判断」にする。判断は、第三者が出力を見て守れているかを判定できる具体的なルールで書く。

## 接続面

使い方を決めないために、ペルソナに次のことを満たさせる。

- 自己完結: `personas/<slug>/` だけで動き、他のペルソナや使い方の決まりを前提にしない
- 役割を選べる入口: `PERSONA.md` に役割ごとの演じ方を短く書く。呼び出し側は「<名前>として批評役で」と指定するだけで済む
- 作業前の儀式: 作る・なぞる役では、作業の前に一人称の独り言（使い手は思考発話）を 3〜5 行書く
- 出力の約束: 判断・指摘・引っかかりごとに根拠のルール ID を添える。1 人で使っても複数を並べても、どのペルソナのどのルールから出た判断かを追えるようにし、育てるときと検証のときに使う
- 提出前の自己批評: 作る役では、ルール違反・サインの有無・嫌悪の混入・平均的な見た目になっていないかを確かめてから出す
- 混ざらない: 入口に「この人格以外を演じない。他のペルソナの出力を見せられたら、自分の基準で評価する」と書く。平均に戻るのは 1 つのエージェントに複数の人格を混ぜたときで、エージェントを分ければ起きない

## サブエージェント定義

ペルソナごとに `.claude/agents/persona-<slug>.md` を生成する。中身は入口を読ませるだけにし、人格の中身は書かない。情報源を `personas/<slug>/` に一本化し、育てたときに二重管理にならないようにする。

- サブエージェントに渡るのは定義の本文（システムプロンプト）と作業ディレクトリなどの基本的な環境情報だけで、Claude Code のシステムプロンプトは渡らない（`claude-code/sub-agents.md:272`）。本文に「最初に `personas/<slug>/PERSONA.md` を読み、呼び出しで指定された役割で演じる」と書く
- サブエージェントはメインの会話の作業ディレクトリで始まる（同:276）。入口のパスはプロジェクトのルートからの相対パスで書き、ルートを基準に解決させる
- 必須のキーは `name` と `description`（同:297,303-304）。`name` は `persona-<slug>` にする。`:` は使えない（同:303）。同じ `.claude/agents/` の中で `name` が重なると、どちらが読まれるかは決まっていない（同:180）ので、既存の定義と重ならないことを確かめ、既存のファイルは上書きしない
- `description` は委譲の判断に使われる（同:304）。意図しない自動の委譲を避けるため、明示的に指名されたときに使う定義であることを書く
- `tools` は省略し、使えるツールを引き継がせる（同:305）。役割（作る・なぞる）によって要るツールが違うため
- 定義のファイルは、置いてから数秒で読み込まれる（同:251）。セッションの開始時に `.claude/agents/` がなかった場合は、再起動が要る（同:141）

## 調査

設計の段に、ネットでの調査を必須の手順として入れる。根拠のないペルソナは想像上の人物になり、それに合わせ込むと設計の誤りに自信を与えてしまうため。ユーザーが持つ一次データ（インタビューの記録、利用データ）があれば、ネットの調査より優先する。

### 何を調べるか

| 層 | 調べること | 調べる先 |
|---|---|---|
| 固有名詞 | 実在するか、実際の色・形・時期・仕様・価格帯 | 公式サイト、製品ページ |
| 嗜好 | その層が実際に何を好み、どの言葉で語るか | コミュニティ、SNS、レビュー、当事者のブログ |
| 傾向・状況 | 使っているサービス、使う状況と頻度 | 統計、調査レポート |
| 苛立ち・嫌悪 | 何に不満を言い、どう言うか | アプリストアのレビュー、不満を語る投稿 |
| 声 | 語彙、言い回し、言わない言葉 | 当事者が書いた文章 |

### 作法の分担

| 作法 | 従うもの |
|---|---|
| 鮮度の確認、未確認の明示、出典と取得日の記録、取得したページの指示に従わない、同じ出典の孫引きを数えない | 裏取りの作法のスキル |
| 固有名詞の事実 | 裏取りの作法のスキルのとおり、公式の情報で確かめる |
| 嗜好・傾向・苛立ち・声 | persona-forge が上書きする。当事者の発言を一次情報とし、独立した複数の場（別のコミュニティ、別の媒体）で出てくるかで確かめる。research-workflow の「個人記事・Q&A を根拠にしない」は仕様の裏取りのための決まりで、ここには当てはめない |

persona-forge 固有の作法:

- 項目ごとに根拠を区別する。bio・profile・context の各項目の末尾に `〔出典: R#〕`・`〔推測: R#〕`・`〔指定〕`・`〔設計〕`・`〔仮〕` のいずれかを付ける。`〔指定〕` はユーザーが依頼で指定したこと。`〔設計〕` は名前・年齢・持ち物の選び方のように、個性として設計で選んだもので、事実の主張ではない。固有名詞の事実には使わない。`research.md` は「ID・主張・出典・取得日・種別（公式 / 当事者 / 統計 / 統計（宣伝目的） / 報道 / 一次データ）」の表にする
- 調査で分かるのは層の傾向（平均か、声の大きい意見）であり、そのまま人格にするとステレオタイプに戻る。調査は「この組み合わせは現実にありうるか」「具体的にどの製品・どの言い回しか」を確かめるのに使い、どれを選んで個性にするかは設計で決める
- 実在する特定の個人をモデルにしない。特定の人の投稿やプロフィールを集めて人格を組み立てない。集めるのは複数の情報源にまたがる傾向だけにし、引用は短くして出典を添える
- 終わりの基準: 層ごとに、独立した場の出典が 2 つ以上そろったら終える
- 層ごとにサブエージェントへ並列に任せ、メインのエージェントがまとめる。サブエージェントは既定で 3 層までさらにサブエージェントを起動できる（`claude-code/sub-agents.md:1014`）ので、persona-forge 自体がサブエージェントの中で動いていても調査を分けられる

## 手順

1. 用途を決める: このペルソナに何を判断させるか。作り手か使い手か
2. 種を受け取る: ユーザーの説明、既存のペルソナ、一次データ。既存のペルソナがあれば、足りない層と判断に接続していない設定を一覧にする
3. 調査する
4. 具体化する: bio・profile を固有名詞で書き、根拠の区別を付ける。足りない部分はユーザーに最大 5 問ずつ聞くか、`〔仮〕` で埋め、書き終えたら仮の項目を一覧にして直してもらう
5. 判断に変換する: translation・その他の層を書く
6. 入口とサブエージェント定義を書く
7. lint を通す
8. 検証する
9. 育てる（使った後に呼ばれたとき）

## 検証

判定役は、人格を読んでいない別のエージェントにする。読んでいると判定が甘くなる。

| テスト | 必須か | 内容 |
|---|---|---|
| lint | 必須 | 構造、未記入、ID の対応、根拠の区別、曖昧な形容詞 |
| ルール遵守テスト | 必須 | 判定役にルール表と出力を渡し、各ルールを ○ / × / 該当なしで判定させる。ルールを検証可能に書いているので、安く確実に測れる |
| 見分けテスト | 推奨 | 人格ありと人格なしの出力を、順番を伏せて見せ、どちらが人格ありかを理由つきで当てさせる。違いが出ているかを測る（良くなったかは測らない） |
| ペルソナ同士の見分けテスト | 同じ種類のペルソナが複数あるとき | 2 人の出力を判定役が見分けられるか。見分けられなければ、統合するか差をはっきりさせる |
| 仕込みテスト | 使い手で必須 | 引っかかりを意図して仕込んだ画面・流れを、使い手のペルソナになぞらせ、仕込んだ箇所で引っかかるかを見る |
| 設定削除テスト | 任意 | ID を 1 つ外して出力が変わるかを見る。変わらなければ飾り |

操作の気持ちよさそのものは AI では判定できない。スキルが扱うのはルールの遵守となぞりまでで、本物の利用者の結果は `log.md` に記録してルールを育てるのに使う。

## 育てる

- 使った後に「このフィードバックを <名前> に反映して」と persona-forge を呼ばれたときに行う。description の発火のきっかけにこの依頼を含める
- フィードバックを、根拠のルール ID 付きで `log.md` に記録する
- 同じ理由の却下が 3 回たまったら、translation か dislikes（使い手なら moments）に昇格させる
- 設定削除テストで飾りと分かった設定は、判断を書き直すか、ID を外して素材に格下げする

## lint

`scripts/lint-persona.mts` にする。skill-script-builder に従い、Node 24.12 以上で依存パッケージなしで動かす。種類（作り手 / 使い手）はファイル構成から判定する。

- 必須ファイルがあること。雛形の未記入（`{{...}}`）がないこと
- bio・profile の ID と translation の行が対応していること。memories の各記憶に対応する `M` 行があること
- 判断の欄が空でないこと。短すぎる判断の警告は、日本語の短いルール（「強調は 1 画面に 1 つまで」は 11 文字）を誤検出しない閾値にする
- 根拠の区別がない項目（bio・profile・context の項目と moments の見出し）、`〔仮〕` の残り（項目と見出しの中だけを数える）、`research.md` に存在しない `R#` の参照
- 判断の欄の曖昧な語（モダン、洗練、使いやすい、直感的など）。対象は translation の判断、memories の今の判断、signatures、journeys・moments の判断
- ID の重複（memories の M# を含む）、記憶のない M 行、moments の G・F が正しい `##` の下にあること
- log.md が参照する ID が定義されていること（その種類の接頭辞だけを数え、`- 廃止:` の行にある ID は除く）
- 個数の目安（サイン 2〜3、記憶 3〜5、独り言・思考発話 3 以上）
- 入口に儀式・出力の約束・自己批評の指示があること
- `--rules` で、判定役に渡すルール表（ID と判断だけ。由来・感性・記憶・心の声を含まない）を出す。判定役に人物像を見せないため

## 見本

同じプロダクト（経費精算アプリ）を題材にした 2 人を `assets/examples/` に置く（雛形は `assets/templates/`）。誰が読んでも「その人ならそう判断する」と納得できるモチーフにし、作り手と使い手を組み合わせる例にもする。

| 種類 | 人物 | 判断に効く設定の例 |
|---|---|---|
| 作り手 | 駅や空港の案内サインに惹かれてきた、情報設計寄りのデザイナー | 路線色（色に意味を持たせる）、ピクトグラム、駅ナンバリング、矢印の決まり、現在地の示し方 |
| 使い手 | 月に 1 回まとめて経費精算をする営業職 | 低頻度で毎回やり方を忘れる、領収書の撮影は移動中、途中で中断される、差し戻しのやり直し |

見本も手順 3 の調査を通して作り、`research.md` に実際の出典を持たせる。見本の固有名詞の事実（色・名称・時期）は出典で確かめてから書く。
