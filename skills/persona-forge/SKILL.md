# persona-forge スキル

## 目的

人格設定を読ませるだけでは、エージェントは作業に入った瞬間に平均的な判断へ戻る。このスキルは、人格設定を**判断に使われる形**（検証可能なルール）へ変換し、**調査で根拠を持たせ**、効いているかを**測って**育てる。

作るのはペルソナの**データ一式**（`personas/<slug>/`）と、それを読ませるだけの**薄いサブエージェント定義**（`.claude/agents/persona-<slug>.md`）である。演じて作業するのは、それを読んだエージェントであり、このスキルではない。使い方（1 人で使う、複数を並べる、作り手と使い手を往復させる）は呼び出し側がその都度決める。どの使い方でも壊れないように作る。

---

## 作業の間ずっと守ること

| 守ること | 理由 |
|---|---|
| **判断は、第三者が出力を見て守れたか判定できるルールで書く**（「強調は 1 画面に 1 つまで」）。形容詞（モダン、洗練、使いやすい、直感的）で書かない | 形容詞は何も決めず、守れたかを判定できない |
| **設定はカテゴリではなく固有名詞で書く**（「文房具」ではなく製品名と色） | 固有名詞は色・形・質感・使われ方の情報を運ぶ。年齢・性別・職業などの属性だけでは世間の平均像が出る |
| **すべての設定を判断に接続する**。接続できない設定は削るか、素材として ID を付けずに残す | 判断に接続しない設定は出力を変えない |
| **bio・profile・context の各項目に根拠の区別を付ける**（出典あり・出典からの推測・ユーザーの指定・設計で選んだ・仮） | 根拠のないペルソナは想像上の人物になり、それに合わせ込むと設計の誤りに自信を与える |
| **実在する特定の個人をモデルにしない**。集めるのは複数の情報源にまたがる傾向だけにする | 個人の投稿やプロフィールから人格を組み立てると、その人を写し取ることになる |
| **調査の結果をそのまま人格にしない**。調査は「この組み合わせは現実にありうるか」「具体的にどの製品・どの言い回しか」を確かめるのに使い、どれを選んで個性にするかは設計で決める | 調査で分かるのは層の平均か声の大きい意見で、そのまま使うとステレオタイプに戻る |
| **1 つのエージェントに 1 つの人格**。1 つのペルソナに複数の人物を混ぜない | 混ぜると平均に戻る。複数の人物が要るなら、ペルソナを分けて作る |
| **既存のファイルを上書きしない**。直すときは差分を示してから書き換える | 育てたペルソナの記録は作り直せない |
| **判定役には人格を読ませない** | 読んでいると判定が甘くなる |

## 前提

- Claude Code で使う。調査と検証にサブエージェントを使い、`.claude/agents/` に定義を書く
- 調査は、裏取りの作法のスキル（例: [[research-workflow]]）に従う。ただし、嗜好・傾向・苛立ち・声については `references/research.md` の決まりで上書きする。research-workflow の「個人記事・Q&A を根拠にしない」は仕様の裏取りのための決まりで、当事者の発言こそが一次情報になるペルソナの調査には当てはめない
- 同梱の lint は Node.js 24.12 以上で動く。依存パッケージは要らない

---

## ペルソナの種類

最初に、どちらを作るかを決める。

| | 作り手 | 使い手 |
|---|---|---|
| 決めること | 作り手の好みで、どう作るか | 対象の層にとって、どう使えば迷わず気持ちいいか |
| 個性の源 | 好きなもの、持ち物、経歴 | 毎日使っているアプリ、使う状況、慣れている操作 |
| 役割 | 作る / 批評する | なぞる / 批評する |
| 層の書き方 | `references/layers-maker.md` | `references/layers-user.md` |
| 雛形 | `assets/templates/maker/` | `assets/templates/user/` |

対象はデザインのうち、成果物をコード・SVG・構造のあるデータで出せるもの（Web・アプリの UI、LP、スライド、図解、データ可視化、UI の文言、操作の流れ）。ラスター画像の生成、ロゴ・ブランドの立ち上げ、実物のプロダクトは扱わない。出力からルールを守れたかを判定できないか、作る数が少なく検証と育成が回らないため。

---

## 出力

- 既定の保存先は、プロジェクトのルートの `personas/<slug>/`（`slug` は英小文字・数字・ハイフン）。ユーザーが指定すればそれに従う
- サブエージェント定義は `.claude/agents/persona-<slug>.md`。書き方は `references/agent-definition.md`、雛形は `assets/templates/agent.md`
- ファイルの一覧と、演じるときに読むファイルは、各種類の層の書き方の冒頭にある

### ルール ID

判断を持つ項目には ID を付ける。演じるときの出力に根拠として添えさせ、育てるときと検証のときに、どのルールから出た判断かを追う。

| 接頭辞 | 項目 | 置き場所 |
|---|---|---|
| `T` | 設定（bio・profile・context の項目）から導いた判断 | translation.md |
| `M` | 記憶から導いた判断 | translation.md（由来の記憶は memories.md） |
| `S` | サイン（作り手） | signatures.md |
| `D` | 嫌悪（作り手） | dislikes.md |
| `J` | 道のりの期待（使い手） | journeys.md |
| `G` / `F` | 気持ちいい瞬間 / 引っかかる瞬間（使い手） | moments.md |
| `R` | 調査の出典 | research.md |

## 手順

次のチェックリストを写して進める。

```
persona-forge の進み具合:
- [ ] 1. 用途と種類を決めた
- [ ] 2. 種を受け取った
- [ ] 3. 調査した（research.md）
- [ ] 4. 具体化した（bio / profile・context）
- [ ] 5. 判断に変換した（translation ほか）
- [ ] 6. 入口とサブエージェント定義を書いた
- [ ] 7. lint が通った
- [ ] 8. 検証した（log.md に記録）
```

### 1. 用途と種類を決める

「このペルソナに何を判断させるか」を決める。判断させる領域がないペルソナは効かない。例: 管理画面の配色・余白・部品の選び方、UI の文言、スマホでの操作の流れ。複数あれば主な用途を 1 つ決め、まずそれでルールを埋める。作り手か使い手かもここで決める。

### 2. 種を受け取る

- 既存のペルソナがあれば全部読み、層の書き方に照らして「足りない層」「判断に接続していない設定」「根拠のない項目」を一覧にして示す
- ユーザーが一次データ（インタビューの記録、利用データ、問い合わせ、アンケート）を持っていれば受け取る。ネットの調査より優先する
- 足りないことは `references/interview.md` の質問票から、埋まらない部分だけを 1 回に最大 5 問ずつ聞く。答えを待つより、仮で埋めて直してもらうほうが早いことが多い

### 3. 調査する

`references/research.md` に従う。調査役のサブエージェントを、そこに書いた既定の分け方で並列に立て、結果がそろうまで待ってから `research.md` の表にまとめる。層ごとに独立した場の出典が 2 つ以上そろったら終える。

### 4. 具体化する

作り手は `bio.md`、使い手は `profile.md` と `context.md` を書く。カテゴリを固有名詞に置き換え、各項目の末尾に根拠の区別（書き方は層の書き方の「根拠の区別」）を付ける。判断に効かせる項目には `[T1]` のようにタグを付ける。到達すべき具体さは見本で確かめる。作り手は `assets/examples/minato/`、使い手は `assets/examples/itsuki/` にあり、どちらも経費精算アプリを題材にしている。生成の前に、作る種類の見本を一度読む。

書き終えたら、仮で埋めた項目（`〔仮〕` を付けたもの、用途を仮で決めたこと）を一覧にしてユーザーに示し、違うところだけ直してもらう。判断への変換は、仮の項目が直った後のほうが手戻りが少ない。ユーザーが「おまかせ」と言った項目は、そのまま進めてよい。

### 5. 判断に変換する

層の書き方に従い、`translation.md` を先に書き、残りの層を続ける。translation.md の各行の判断は、検証可能なルールにする。記憶から導いた判断も `M` の行として translation.md に入れる。演じるときは memories.md を読まないので、ここに入れないと効かない。

### 6. 入口とサブエージェント定義を書く

雛形の `PERSONA.md` をもとに入口を書く。入口には、人物像の要約、演じるときに読むファイル、役割ごとの演じ方、作業前の儀式、出力の約束（根拠のルール ID を添える）、提出前の自己批評を必ず入れる。続けて `references/agent-definition.md` に従ってサブエージェント定義を書く。見本は `assets/examples/agents/` にある。同じ `name` の定義がすでにないことを確かめ、既存のファイルは上書きしない。

### 7. lint を通す

```
node "${CLAUDE_SKILL_DIR}/scripts/lint-persona.mts" <ペルソナのディレクトリの絶対パス>
```

- 作り手か使い手かは、ファイルの構成（`bio.md` か `profile.md` か）から判定する
- 結果は JSON で stdout に、要約は stderr に出る。終了コードは 0（error なし）、1（error あり。検査の途中で失敗したときも 1 で、JSON の `ok` が null になる。null なら検査できていない）、2（使い方の誤り。ディレクトリがない、種類を判定できない）
- `error` はすべて直す（必須のファイルがない、未記入の `{{...}}` がある、ID と行が対応しない、判断が空、根拠の区別がない、出典の ID が research.md にない、など）
- `warning` は中身を見て判断する（判断に曖昧な形容詞がある、仮が残っている、個数が目安から外れている、など）
- `--rules` を付けると、検査はせず、判定役に渡すルール表（ID と判断だけ。人物像を含まない）を Markdown で出す。手順 8 で使う

### 8. 検証する

`references/evaluation.md` に従う。最低限、**ルール遵守テスト**は必ず行い、使い手では**仕込みテスト**も必ず行う。結果を `log.md` に記録し、不合格なら手順 4 か 5 に戻る。

---

## 育てる

使った後に「このフィードバックを <名前> に反映して」と呼ばれたときに行う。

1. フィードバック（採用・却下・批評・本物の利用者での結果）を、根拠のルール ID 付きで `log.md` に追記する。ID が分からなければ、出力に添えられた ID か、該当しそうなルールを示して確かめる
2. 同じ理由の却下が 3 回たまったら、作り手なら translation.md か dislikes.md、使い手なら translation.md か moments.md にルールとして昇格させる
3. 設定削除テストで飾りと分かった設定は、判断を具体的に書き直すか、ID を外して素材に格下げする
4. 直したら lint を通し、変えた ID についてルール遵守テストをやり直す

## Gotchas（既知の注意点）

- **見分けテストに合格しても、出力が良くなったとは限らない**。測れるのは「人格なしと違うか」だけ。見分けテストに合格しても、ルール遵守テストを省かない
- **操作の気持ちよさそのものは、エージェントには判定できない**。使い手のペルソナで確かめられるのは、ルールを守っているかと、なぞって引っかかる箇所まで。本物の利用者の結果は log.md に入れてルールを育てる
- **サブエージェントには、定義の本文と作業ディレクトリなどの基本的な環境情報しか渡らない**。会話の文脈もこのスキルも渡らないので、入口のパスは定義の本文に書く
- **同じ `.claude/agents/` の中で `name` が重なると、どちらの定義が読まれるかは決まっていない**。`persona-` を付けた名前にし、書く前に既存の定義を確かめる
- **セッションの開始時に `.claude/agents/` がなかった場合、新しく作った定義はそのセッションでは見つからない**。ユーザーに Claude Code の再起動を頼む
- **調査役のエージェントは、指示しないとコミュニティの声を根拠から外す**（仕様の裏取りの作法を当てはめてしまう）。調査を任せるときは、当事者の発言を一次情報として扱うことを依頼文に書く
- **記憶は演じるときに読まれない**。記憶から出た判断は translation.md の `M` 行にしないと効かない
- **「使い手を想像で埋めた」ことは、出力からは見分けられない**。仮の項目は lint で数え、残っていることをユーザーに伝える
